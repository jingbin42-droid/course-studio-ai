# Course Studio AI 团队工作流

## 1. 工作流目标

Course Studio AI 是三人团队的“AI 课程团队工作与经营中枢”。本工作流让 A、B、C 围绕同一门课程，同时运行团队工作闭环和课程经营闭环，并保持每个人每天的操作足够简单。

系统不要求团队为了“维护项目管理工具”而工作。成员只需明确承诺、记录事实、提交交接和确认计划；AI 负责整理、汇总和提示，但不代替成员承诺。

整体结构是：**一个课程项目、两个业务闭环、一个 AI 全能合伙人**。

```text
团队工作闭环：每日规划 → 执行 → 自然语言记录 → AI 整理
             → 个人日报 → 团队日报 → 明日计划 → 次日执行

课程经营闭环：课程定位 → 制作 → 宣传 → 上线销售 → 经营数据
             → AI 分析 → 优化建议 → 确认后创建改进任务
```

两个闭环通过课程项目、任务、交接和业务日期共享事实。经营分析产生的改进任务回到团队工作闭环，完成后的经营结果继续验证改进效果。

## 2. 三条协作主线

| 主线 | 负责人 | 典型产出 | 主要上下游 |
| --- | --- | --- | --- |
| 课程制作 | A | 课程大纲、脚本、录制文件、成片 | 向 B 提供卖点与素材；向 C 提供可上线课程 |
| 宣传与视觉 | B | 海报、详情页文案、宣传短视频、发布素材 | 依赖 A 的课程信息；向 C 交付渠道物料 |
| 上线与运营 | C | 上架配置、发布排期、运营记录、反馈与复盘 | 验收 A/B 产出；将反馈回流给 A/B |

三条主线不能拆成三个孤岛。所有工作项都归属于同一课程项目，通过依赖和交接相连。

## 3. 团队初始化与业务日期

### 3.1 初始化流程

1. 首位管理员创建团队，成为团队 `owner`，并选择自己的 A/B/C 业务职责。
2. owner 邀请另外两名成员，并为邀请预设 `member` 团队角色和 A/B/C 业务职责。
3. 受邀成员首次登录并接受邀请后，系统将其关联到同一个团队。
4. 三人可在团队设置中确认成员身份；MVP 由 owner 管理邀请、职责调整和团队配置。

`owner` / `member` 是系统管理角色；A/B/C 是业务职责。二者必须分开保存，不能用 A/B/C 决定系统管理权限。

### 3.2 团队时区与业务日期

- 每个团队配置一个 IANA 时区，例如 `Asia/Shanghai`，但该值不是所有团队的固定值。
- 团队业务日期是事件时间转换到团队时区后的本地日历日期，边界为当地时间 00:00 至次日 00:00。
- 工作记录默认归入提交时的团队业务日期；补记时可由成员明确选择历史日期。
- 日报统计指定业务日期内的团队事实；明日计划的日期是下一个团队业务日期。
- 团队时区之后发生变化时，已经保存的历史业务日期不重新计算。

## 4. 团队工作闭环

### 4.1 开始工作：确认今日聚焦

每位成员进入“今日工作台”，依次处理：

1. 查看 AI 建议并已由自己确认的今日重点。
2. 查看待接收交接、待修改反馈和需要审核的内容。
3. 查看谁在等待自己的产出，以及自己被什么阻塞。
4. 查看距离课程上线和正式销售分别还缺少哪些任务、里程碑或验收。
5. 查看 AI 下一步建议，根据突发变化调整今日重点；若影响他人，补充说明或更新依赖。

今日重点建议控制在 1–3 项。普通待办仍可存在，但不应挤占首页决策空间。

### 4.2 工作中：更新关键事实

成员在以下时刻更新系统：

- 开始或完成一个关键工作项；
- 发现阻塞、日期风险或上游变更；
- 形成可供他人使用的产出；
- 收到交接并验收或提出修改；
- 做出会影响课程、宣传或上线的重要决定。

不要求逐分钟记录。重要的是让下游能判断“是否可以开始”和“使用哪个版本”。

### 4.3 随手记录：自然语言输入

成员可随时输入自由文本。推荐但不强制包含：

- 做了什么；
- 结果或产出在哪里；
- 遇到什么问题；
- 下一步是什么；
- 需要谁帮助。

AI 提取后展示建议，例如“将任务标记为完成”“创建一个阻塞”“向 C 发起交接”。成员逐项确认，未确认内容只保留为 AI 草稿。

记录可设为团队可见或私人。私人记录只有作者本人可查看，不进入团队日报，也不能被其他成员的 AI 请求读取。

### 4.4 收尾：日报与明日计划

每天收尾时：

1. 成员主动触发生成；AI 汇总个人当日记录、工作项变化和交接，生成个人日报草稿。
2. 成员检查事实、补充缺失并确认。
3. 用户主动触发团队日报；AI 只汇总团队可见且可追溯的事实，生成团队日报草稿；指定成员或团队共同确认。
4. AI 根据未完成事项、依赖和里程碑，生成每人明日 1–3 个重点。
5. 每个人确认或调整自己的计划；确认内容次日进入“今日聚焦”。

如果某人当天未记录，团队日报明确显示“信息缺失”，不能由 AI 猜测其进度。

明日计划与工作项的关系：

- 安排已有工作时引用原 `work_item_id`。
- 建议新增工作时先形成新任务提案，成员确认后才创建工作项。
- 纯建议可以保留在计划中，不自动创建任务。
- 只有已确认计划进入次日首页。
- 确认计划不改变原工作项截止日期；如需改期，必须作为独立动作确认。

## 5. 课程经营闭环与生命周期

课程经营闭环覆盖课程定位、制作、宣传、上线销售、经营记录、分析和优化。课程阶段提供共同语言，不是严格的流水线；宣传工作可以在制作阶段提前开始，经营反馈也可能让课程重新进入制作或宣传。

### 5.1 `idea`：选题

目标：判断课程是否值得做。

关键内容：

- 目标学员和问题；
- 课程核心承诺；
- 初步形式和范围；
- 已知风险或验证问题。

阶段出口：团队同意进入策划，并明确课程负责人。

### 5.2 `planning`：策划

目标：形成可执行的课程和发布计划。

A：课程结构、章节、脚本计划、录制需求。

B：核心卖点、视觉方向、宣传内容清单。

C：上线渠道、目标日期、上架要求、运营假设。

阶段出口：核心范围清楚，关键里程碑和首批工作项已建立，重大依赖可见。

### 5.3 `production`：制作

目标：产生可审核、可上线的课程内容。

A 主导脚本、录制、剪辑；B 可并行提炼卖点和准备视觉；C 提前检查平台规格和上线清单。

关键交接：

- A → B：课程定位、卖点、讲师/课程视觉素材、可引用片段。
- A → C：章节结构、成片/文件、封面与字幕需求、版本说明。
- C → A：平台格式检查结果和修改要求。

阶段出口：课程核心内容达到可上线标准；未完成项和例外被明确记录。

### 5.4 `promotion`：宣传准备

目标：形成与课程内容一致的宣传材料和发布计划。

B 主导海报、详情文案、短视频等；A 确认专业内容与课程承诺；C 确认渠道规格、发布时间和使用方式。

关键交接：

- B → A：需要内容准确性确认的文案或剪辑。
- B → C：已审核宣传物料、版本和渠道使用说明。
- C → B：渠道尺寸、标题限制、发布时间和修改反馈。

宣传可与制作并行，但任何依赖未定稿课程内容的物料都应标为草稿或风险。

### 5.5 `launch`：上线发布

目标：课程与宣传内容按计划正确发布。

C 主导上线清单：

- 课程文件、章节、价格/权限等配置已确认；
- 页面、海报、文案和短视频使用正确版本；
- 链接、时间、渠道和负责人明确；
- 发布后检查和异常处理路径明确。

A/B 处理上线前最后的内容或物料问题。关键发布动作完成后记录结果与链接。

阶段出口：课程已上线，主要宣传动作已执行，运营观察项已建立。

“课程上线”表示课程内容和承载页面达到可访问、可交付状态；“正式销售”还要求定价/购买链路、宣传物料、发布排期和必要运营准备完成。两者可设置不同目标日期，并在首页分别展示剩余事项。

### 5.6 `operation`：运营

目标：根据真实反馈持续改进课程和宣传。

C 记录渠道表现、用户问题、反馈和运营动作；AI 可整理主题，但数据和结论需标明来源。需要内容修改时，由 C 创建或建议创建工作项，并与 A/B 完成交接。

P1 可按渠道和业务日期记录聚合的曝光、点击、咨询、订单和销售额，并形成宣传效果复盘。只记录聚合指标，不保存客户姓名、电话、账号、聊天内容或其他个人隐私数据。

数据缺失时保持为空并显示“尚未记录”，不能使用 0 或 AI 推测补齐。AI 只在真实数据存在时比较渠道与时间段表现、分析宣传和销售结果，并将优化建议保存为草稿。需要执行的建议必须由用户确认创建改进工作项或交接，之后重新进入团队工作闭环。

运营复盘至少回答：

- 什么有效，证据是什么；
- 什么没有达到预期；
- 哪些内容、宣传或流程需要改进；
- 哪些经验应沉淀到知识库；
- 下一轮课程应复用或避免什么。

### 5.7 `archived`：归档

课程不再活跃推进时归档。归档不会删除工作记录、日报、资产和知识；仍可检索和引用，但默认不出现在活跃工作台。

## 6. 工作项状态流转

```text
backlog → ready → in_progress → review → done
              ↘ blocked ↗
任意未完成状态 → cancelled
```

- `backlog`：有价值但尚未承诺近期执行。
- `ready`：信息和前置条件基本齐全，可开始。
- `in_progress`：负责人正在推进。
- `blocked`：当前无法继续，必须写明原因。
- `review`：工作产出完成，等待审核或接收。
- `done`：工作项完成；若存在交接，不代表交接自动验收。
- `cancelled`：不再需要，并保留原因和历史。

状态不是精确工时追踪工具。成员只需在影响协作判断时更新。

## 7. 依赖工作流

### 7.1 创建依赖

当下游确实无法开始或完成时，才建立依赖，避免把所有相关事项都连成复杂网络。

示例：

- “制作课程详情页文案”依赖“确认课程核心卖点”。
- “平台正式上架”依赖“最终成片验收”。

### 7.2 阻塞处理

工作项进入 `blocked` 时，需要：

- 简述阻塞原因；
- 若明确，关联前置工作项或需要协助的成员；
- 说明期望解除条件。

首页向阻塞方和被等待方展示。前置工作完成后，系统提示依赖已解除，由负责人决定是否恢复 `ready` 或 `in_progress`。

### 7.3 避免依赖滥用

- 仅仅“最好先看看”不一定是硬依赖。
- 不使用依赖表达层级；大任务可通过里程碑或拆分工作项处理。
- AI 可提示潜在依赖，但必须由成员确认。

## 8. 交接工作流

### 8.1 提交交接

交付人选择关联工作项，填写：

- 交付物名称与链接；
- 接收人；
- 版本或状态；
- 使用说明和需重点检查的内容。

交接状态为 `submitted`，进入接收人的“待我处理”。

### 8.2 接收与反馈

接收人可选择：

- `received`：已收到，尚在检查；
- `changes_requested`：需要修改，并说明问题；
- `accepted`：已验收，可用于下游工作；
- `cancelled`：该交接已失效。

退回修改后，交付人修订产出并重新提交。每次提交、反馈和重提都追加到 `handoff_events`，不得覆盖之前的反馈。

### 8.3 交接事件历史

一条交接拥有当前状态，同时按时间顺序保存以下事件：

- `submitted`：首次提交；
- `received`：接收人确认收到；
- `changes_requested`：接收人要求修改并留下反馈；
- `resubmitted`：交付人提交新版本及说明；
- `accepted`：接收人验收通过；
- `cancelled`：交接取消并说明原因。

事件记录操作者、发生时间、版本/产出链接和说明。多次 `changes_requested` 与 `resubmitted` 可以循环出现，历史保持完整。`handoffs` 保存当前状态，`handoff_events` 保存全过程。

### 8.4 交接完成的含义

只有 `accepted` 才表示接收方确认可用。工作项 `done` 与交接 `accepted` 分开，允许以下真实情况：

- A 认为剪辑已完成，但 C 检查后要求修改格式。
- B 完成海报，但 C 尚未确认渠道尺寸。
- C 已收到草稿，仅用于排期，不代表最终验收。

## 9. 角色的典型日常流程

### 9.1 A 的一天

1. 查看今日录制/剪辑重点及 B/C 的素材等待。
2. 处理被退回的内容问题或关键审核。
3. 推进脚本、录制、剪辑，必要时记录阻塞。
4. 形成可用版本后在交接中填写产出链接、版本和说明，并提交给 B/C。
5. 用自然语言记录完成、问题和下一步。
6. 确认个人日报和次日制作重点。

### 9.2 B 的一天

1. 查看待接收课程素材、待确认文案和渠道截止时间。
2. 确认上游版本及课程卖点，避免基于过时信息制作。
3. 推进海报、文案和短视频，标记需 A 审核的内容。
4. 将审核后的物料交接给 C，并说明渠道用途和版本。
5. 记录创意选择、阻塞及下一步，必要时沉淀品牌知识。
6. 确认个人日报和次日宣传重点。

### 9.3 C 的一天

1. 查看课程上线里程碑、待验收内容和宣传物料。
2. 检查交付物格式、版本、链接和渠道要求。
3. 推进上架、排期、发布和发布后检查。
4. 记录运营动作、反馈和异常；对需要改进的内容发起工作项或交接。
5. 更新课程风险和关键项目动态。
6. 确认个人日报，协调团队日报和次日共同重点。

## 10. 课程变更与决策记忆

课程内容、上线时间或宣传口径变化时：

1. 在课程项目中记录变更事实和原因。
2. 找出受影响的工作项、资产和已提交交接。
3. 负责人确认哪些任务需要重开、修改或取消。
4. AI 可以生成影响清单，但不能自动批量修改。
5. 首页向受影响成员显示变化，团队日报记录重要决策。

任何“最终版”发生变化，都应产生新版本说明，不能只替换链接而不告知下游。

P1 中，影响课程范围、宣传承诺、上线/销售日期或运营策略的重要决定，使用 `knowledge_entries` 的 `decision` 分类记录：决策内容、原因、参与成员、影响范围、关联工作项和后续跟进。不增加独立决策流程或审批系统。

## 11. AI 参与边界

AI 可以：

- 从记录中提取完成项、阻塞、下一步和候选关联；
- 汇总个人和团队日报；
- 根据依赖和里程碑建议优先级；
- 找出可能遗漏的交接和检查项；
- 检索知识并解释建议来源。
- 基于已确认课程信息辅助宣传文案、短视频结构和详情页框架；
- 在 P1 有真实经营数据时分析宣传与销售结果，提出优化建议。

AI 不可以未经确认：

- 宣布成员已经完成某项工作；
- 改变负责人、截止日期、课程阶段或工作项状态；
- 代表成员接收或验收交接；
- 将推断写入正式日报；
- 对外发布内容。
- 编造曝光、点击、订单、销售额或任务完成率；
- 把相关性描述成已经证实的经营因果关系。

MVP 日报只由用户主动触发；不设置定时任务、自动通知或多 Agent 自动执行。AI 服务架构继续保留统一上下文、结构化输出、来源引用和动作确认机制。

## 12. 最小协作规范

为让系统提供可靠帮助，团队只需共同遵守：

1. 关键工作属于某门课程并有明确负责人。
2. 被阻塞时说明原因，不让任务静默停滞。
3. 可供他人使用的产出通过交接发送。
4. 每天至少留下一条真实工作记录或确认“今日无进展”。
5. AI 产物在成为团队事实前由相关成员确认。

这五条比增加更多字段、提醒和审批更重要。

## 13. 分阶段工作流边界

### P0：先闭合团队日常工作

- 团队初始化、邀请、权限和团队时区；
- 今日工作台、课程项目、任务、依赖、阻塞和交接历史；
- 自然语言记录、AI 整理、个人/团队日报和明日计划；
- AI 项目问答、轻量宣传草稿和经确认的动作建议。

### P1：再闭合课程经营与团队记忆
