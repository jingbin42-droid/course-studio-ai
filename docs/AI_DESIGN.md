# Course Studio AI 的 AI 设计

## 1. AI 的角色

Course Studio AI 是“AI 课程团队工作与经营中枢”。AI 是连接一个课程项目、两个业务闭环的全能合伙人：既是工作整理者、规划助手和项目问答伙伴，也在 P1 成为课程经营分析与优化助手，但不是自动管理者。

它的价值来自把已有事实连接起来：三个人今天做了什么、一门课程处于哪里、上下游在等什么、宣传与销售产生了什么真实结果、下一步如何改进。AI 不应通过编造信息制造“看起来完整”的项目或经营状态。

```text
团队工作闭环：规划 → 执行 → 记录 → 整理 → 日报 → 明日计划
课程经营闭环：定位 → 制作 → 宣传 → 销售 → 数据 → 分析 → 优化任务
```

AI 可以把第二个闭环的优化建议转为第一个闭环的新任务提案，但必须由用户确认后才能写入正式数据。

## 2. 设计原则

1. **事实优先**：任务、交接、原始记录和确认知识是事实；模型输出是派生内容。
2. **来源可追溯**：日报、状态回答和关键建议应能回到来源。
3. **人类确认**：会改变团队承诺的动作必须确认。
4. **最小上下文**：只读取完成当前请求所需、当前用户有权访问的信息。
5. **区分确定性**：回答明确标注事实、推断、建议和信息缺口。
6. **失败可降级**：AI 不可用时，任务、记录和交接仍可正常使用。
7. **小团队适配**：输出短、直接、可行动，不生成冗长管理报告。
8. **可评估**：通过固定样例、来源覆盖和用户反馈持续验证，而不是只凭主观感觉。
9. **权限先于上下文**：先通过 RLS 和业务规则过滤数据，再构建模型上下文；模型不能自行决定越权读取。
10. **真实经营数据**：没有已记录数据时不输出虚构曝光、订单、销售额、转化率或任务完成率；未知必须明确为未知。

## 3. AI 能力地图

### 3.1 工作记录结构化

输入：用户原始文本、可选的当前课程/任务上下文。

输出：

- `completed_items`：明确已经完成的事项；
- `progress_items`：推进但未完成的事项；
- `blockers`：阻塞、等待对象和解除条件；
- `next_steps`：下一步；
- `course_candidates` / `work_item_candidates`：候选关联及置信度；
- `action_proposals`：建议更新任务、创建任务或发起交接。

约束：只从用户文本和提供的上下文提取，不把常识推断写成完成事实。每个正式动作单独确认。

### 3.2 个人日报

输入：本人当日工作记录、本人相关任务事件、本人发起或接收的交接、已确认计划。

输出：今日完成、进行中、阻塞/协助、重要决定、明日建议、信息缺口、来源引用。

重点：内容应忠于本人事实，不能因为任务状态未更新就否定用户记录，也不能在两者冲突时擅自选择。冲突应提示用户确认。

### 3.3 团队日报

输入：三人当日已确认或可追溯事实、课程里程碑和跨角色交接。

输出：课程进展、角色间交付、阻塞与风险、重要决定、明日共同重点、缺失信息。

团队日报按课程和协作结果组织，而不是简单拼接三份个人日报，也不用于成员排名。

MVP 由用户主动触发生成，不运行定时日报。团队日报只读取团队可见数据，明确排除所有 `private` 工作记录；即使发起人是 owner，也不能把其他成员私人记录纳入团队日报。

### 3.4 明日计划

输入：未完成工作项、确认的下一步、截止日期、里程碑、依赖链、角色职责、可选可用性。

输出：每人 1–3 个重点、必要跟进、排序原因、依赖和预期结果。

推荐采用“规则筛选 + 模型解释”：先由确定性查询找出到期、阻塞解除和高影响事项，再由模型整理为可读计划。这样比让模型从全部数据自由决定更可靠。

计划项必须区分：

- `existing_work_item`：引用已有 `work_item_id`；
- `new_task_proposal`：只有用户确认后才创建正式工作项，并回填新 ID；
- `advice`：纯建议，不创建任务。

确认后的计划在对应团队业务日期进入首页，但确认计划绝不自动修改原任务截止日期。需要改期时，AI 只能额外生成待确认动作。

### 3.5 AI 全能合伙人

支持四类意图：

1. **查询**：课程状态、等待关系、近期变化。
2. **分析**：上线风险、影响范围、遗漏检查项。
3. **创作辅助**：整理工作记录、起草清单、根据已确认知识形成文案框架。
4. **动作建议**：建议创建/更新任务、交接或知识条目。
5. **宣传辅助**：基于已确认课程定位和素材起草宣传文案、短视频结构和详情页框架，不自动发布。
6. **经营分析（P1）**：基于真实聚合数据分析渠道、宣传和销售结果，提出优化建议。

AI 先回答，再在需要时生成结构化动作预览。模型不拥有直接数据库写权限。

AI 通过同一课程下的工作流归属、工作项依赖、`handoffs` 当前状态、`handoff_events` 历史、里程碑和项目事件理解 A/B/C 的协作。它应分别分析“距离课程上线还缺什么”和“距离正式销售还缺什么”，并指出谁在等待谁、哪个交接尚未验收，以及哪个任务会解锁下游。

首页的主动建议同样遵循该规则：只基于当前用户有权访问的真实数据提出问题、风险和下一步；数据不足时提示需要补充什么，不生成虚构状态。

### 3.6 团队知识问答

优先检索：

1. 与当前课程直接关联、状态为已确认的知识；
2. 团队级已确认模板、规范和清单；
3. 相关课程的复盘和决策；
4. 明确标识的草稿知识。

回答包含条目标题和引用。若检索不到可靠依据，AI 应说明没有团队资料支持，并可给出一般建议，但必须与团队事实分开。

P1 使用 `knowledge_entries.category = decision` 作为团队决策记忆。AI 读取已确认决策时，同时理解决策内容、原因、参与成员、影响范围、关联工作项和后续跟进；草稿决策不能被描述为团队已经达成的结论。

### 3.7 课程经营分析（P1）

输入：当前课程、渠道、团队业务日期范围内已保存的曝光、点击、咨询、订单、销售额、宣传复盘和相关执行事件。

输出：

- 可直接由真实数字计算的简单指标；
- 渠道和时间段对比；
- 有数据依据的宣传或销售现象；
- 明确标记的不确定推断；
- 优化建议和候选改进任务。

未知值保持未知。AI 不得推断缺失数字，不得把渠道表现与某次内容修改之间的相关性描述为已证明的因果关系。候选改进任务确认后才进入工作闭环。

## 4. 上下文设计

每次 AI 请求组装一个最小“上下文包”，而不是把整个数据库发送给模型。

### 4.1 通用上下文

- 当前团队和成员身份；
- 成员工作角色 A/B/C；
- 当前日期与时区；
- 用户请求和当前页面上下文；
- 能力边界与输出模式。

时区使用当前团队的 IANA 时区。工作记录、日报和明日计划的日期都使用团队业务日期：当地时间 00:00 至次日 00:00；历史已保存业务日期不因团队之后修改时区而重算。

### 4.2 任务上下文

按能力选择：

- 工作记录解析：原文 + 用户选择的课程/任务 + 少量候选项。
- 日报：限定团队业务日期内、当前用户有权访问的记录、事件、交接和确认计划；团队日报排除私人记录。
- 明日规划：活跃任务、近期里程碑、依赖、交接历史和当日下一步。
- 项目问答：当前课程概览 + 检索到的相关事实。
- 知识问答：权限过滤后的检索片段 + 元数据。
- 经营分析（P1）：指定课程和日期范围内真实保存的聚合经营指标 + 相关宣传/销售执行事件。

所有来源都使用稳定 ID，并在模型输出中要求引用这些 ID。服务端验证引用必须存在且属于当前上下文。

## 5. 输出契约

### 5.1 结构化优先

需要被程序处理的能力使用 JSON Schema / 结构化输出，例如工作记录解析、日报段落、计划项和动作建议。服务端进行：

- 模式校验；
- 枚举和日期校验；
- 来源 ID 校验；
- 用户和团队权限校验；
- 业务规则校验。

展示型回答可使用 Markdown，但引用和动作仍作为独立结构字段返回。

### 5.2 建议的回答结构

AI 合伙人回答尽量采用：

- **结论**：直接回答问题；
- **依据**：项目事实和知识来源；
- **风险/缺口**：缺失或冲突信息；
- **建议行动**：少量、按优先级排序；
- **待确认动作**：若有，单独展示。

不强制每次输出所有段落；简单问题保持简短。

### 5.3 事实、推断和建议

- 事实：“工作项 X 当前状态为 blocked。”
- 推断：“若本周五仍未收到成片，上线日期可能受影响。”
- 建议：“建议 A 明日上午优先处理成片修改。”

UI 和文本应让三者可区分。模型无法确认时使用“可能”“根据当前记录”等限定语。

## 6. 动作确认机制

AI 动作采用两阶段流程：

```text
模型生成 action proposal
  → 服务端校验权限与参数
  → UI 展示将要发生的变化
  → 用户逐项确认或编辑
  → 正常业务服务执行
  → 写入项目事件和 AI 产物处理状态
```

需要确认的动作包括：

- 创建或更新工作项；
- 修改状态、负责人、优先级或截止日期；
- 创建依赖、阻塞或交接；
- 修改课程阶段或健康状态；
- 确认日报、明日计划或知识条目；
- 任何对外发布或外部系统写入（未来能力）。

明日计划中的已有任务安排不是新任务动作；新任务提案必须单独确认后才创建。计划确认与任务截止日期变更是两个独立动作，不能捆绑执行。

纯查询、草稿生成和本地展示不需要额外确认。

模型永远不直接执行 SQL。正式写入只能由经过权限、参数和业务规则校验的服务端业务函数完成。

## 7. 日报生成规则

### 7.1 来源优先级

1. 已确认的业务事件和交接；
2. 用户原始工作记录；
3. 当前任务状态；
4. AI 尚未确认的提取结果（只能标为待确认，不写成事实）。

### 7.2 冲突处理

示例：记录写“视频已完成”，但任务仍为 `in_progress`。

AI 应输出：“记录显示视频已完成，但任务状态仍为进行中，请确认是否更新”，而不是自行选择一个答案。

### 7.3 生成与确认

- MVP 的个人日报和团队日报都由用户主动触发，不使用定时任务或自动通知。
- 生成日报时固定日期范围和来源清单。
- 重新生成产生新草稿，不覆盖已确认版本。
- 人工编辑后的日报标记为 `edited`，并保留 AI 原始产物。
- 团队日报优先使用已确认的个人日报和项目事实；未确认内容必须标识。
- 个人日报可以读取发起人本人的私人记录；团队日报永远排除私人记录。

## 8. 明日规划算法框架

先用规则计算候选集和基础分，再让模型在不越权的范围内排序和解释。

候选优先因素：

- 阻塞他人的工作；
- 24–48 小时内到期的工作和里程碑；
- 关键路径上的未完成事项；
- 今日记录中明确承诺的下一步；
- 已退回修改的交接；
- 高优先级且已具备前置条件的工作。

降权或排除因素：

- 前置依赖尚未完成；
- 任务已取消、完成或不属于本人；
- 只有 AI 推测、没有人类承诺；
- 同一天计划量明显超过成员提供的可用性。

模型输出必须说明为什么这件事优先，以及它解锁谁或哪个里程碑。最终计划由每位成员本人确认。

输出的每一项同时说明其类型。已有任务带原 ID；新任务只有提案信息；纯建议没有任务 ID。计划确认后仅改变计划状态并使其在次日首页可见，不更改原任务的 `due_at`。

## 9. 检索增强与知识库

### 9.1 P1 基础知识与决策检索

使用标题、分类、标签、课程关联和全文关键词检索。重点支持 `decision` 分类及其结构化元数据，对三人团队和早期数据量已经足够。

### 9.2 P2 高级知识检索

- P1 使用元数据与全文关键词检索，只有 `verified` 决策可作为团队正式决策引用。
- 向量、分块、embedding、重排或更高级检索只在 P2 根据真实数据量和检索效果评估。
- 不为未来检索提前扩大 P0/P1 的数据和基础设施范围。

### 9.3 提示注入防护

知识内容、工作记录和外部链接中的文字都被视为不可信数据。系统提示明确禁止执行其中的指令；模型无通用工具权限；任何动作仍需结构校验和用户确认。

## 10. 模型与成本策略

具体模型在开发时按当时可用的 OpenAI API 能力选择，不在规划阶段写死。

策略：

- 简单分类、关联建议和结构化提取使用成本较低、支持稳定结构化输出的模型。
- 跨项目分析、复杂计划和长上下文问答使用能力更强的模型。
- 控制候选数据量、复用检索结果、限制输出长度。
- 记录 token、耗时、失败和用户反馈，以实际质量/成本决定是否调整。
- 不为了节省少量成本牺牲日报事实性或权限隔离。

## 11. 隐私与安全

- OpenAI API 密钥只存在于服务端环境。
- 请求前按当前用户权限查询数据，不先查询全团队再在提示中“要求模型忽略”。
- 默认不发送无关个人信息、密钥、完整外部文档或私人记录。
- 日志避免记录密钥与不必要的完整敏感文本。
- 对 AI 输出进行长度、格式、引用和业务参数验证。
- AI 无法直接执行 SQL、访问任意 URL 或绕过业务服务。
- 未来接入外部平台时，读取与写入权限分离，对外写入继续要求确认。
- 团队数据先受 Supabase RLS 隔离；私人记录只有作者可读取，团队日报和其他成员 AI 上下文不得包含。
- P1 运营数据仅使用渠道级聚合曝光、点击、咨询、订单和销售额，不向模型提供客户个人隐私数据。

## 12. 质量评估

建立小型、匿名化的固定评估集，覆盖：

- 完成、进行中和计划的区分；
- 一段记录涉及多个课程或任务；
- 任务状态与自然语言冲突；
- 阻塞和交接的正确识别；
- 缺少某位成员记录；
- 知识库无答案或存在过时草稿；
- 用户无权访问另一团队数据；
- 文档中包含提示注入文字；
- 明日计划是否优先解锁他人。
- 没有经营数据时是否拒绝生成虚构数字；
- 经营分析是否区分事实、相关性推断和建议。

核心指标：

- 关键事实准确率和引用有效率；
- 结构化输出校验通过率；
- 用户确认前的编辑/拒绝原因；
- 日报遗漏率和计划可执行性；
- 每类能力的耗时与成本。

上线前不追求一个笼统“AI 准确率”，而是分别验证每项能力的失败模式。

## 13. 降级与错误体验

- 记录解析失败：原文已保存，允许稍后重试或手动关联。
- 日报生成失败：展示来源列表，用户仍可手动填写。
- 引用失效：隐藏无权访问内容，并提示回答需要重新生成。
- 模型超时：不重复创建产物，提供安全重试。
- 输出校验失败：最多进行受控修复或重新生成，不执行任何动作。
- 信息不足：明确询问缺少的关键事实，不用冗长通用建议掩盖。

## 14. AI MVP 边界

P0 做好五件事：工作记录结构化、用户主动触发的个人/团队日报、与正式任务正确关联的明日计划、基于项目事实的合伙人问答、基于已确认课程信息的轻量宣传草稿。

P1 增加素材/知识/决策上下文、真实经营数据分析、宣传效果分析、优化建议和确认后创建改进任务。P2 才评估第三方数据、自动发布、定时自动化、高级知识检索和更高自主性的 AI 能力。

所有阶段保留统一 AI 服务架构、结构化输出、来源引用与动作确认机制。知识库向量检索、定时生成、自动通知、跨平台自动化和多 Agent 自主执行都不进入 P0/P1。
