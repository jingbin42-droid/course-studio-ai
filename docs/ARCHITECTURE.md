# Course Studio AI 系统架构

## 1. 架构目标

Course Studio AI 的定位是“AI 课程团队工作与经营中枢”。系统围绕一个课程项目承载两个共享数据的闭环：P0 的团队工作闭环，以及 P1 的课程经营闭环；AI 全能合伙人在权限和人工确认边界内连接二者。

- 团队工作闭环：规划、执行、记录、AI 整理、日报和明日计划。
- 课程经营闭环：定位、制作、宣传、上线销售、真实经营数据、AI 分析和改进任务。

系统不是 CRM，不保存客户档案或个人隐私数据，也不建设复杂财务系统。没有真实数据时不得展示虚构经营数字或任务完成率。

首版采用模块化单体，不拆微服务。选择成熟平台能力，减少运维和集成成本，同时确保权限、AI 可追溯性和后续演进空间。

## 2. 技术选型

| 层级 | 计划选型 | 用途 |
| --- | --- | --- |
| Web 应用 | Next.js App Router + TypeScript | 页面、服务端渲染、Server Actions / Route Handlers |
| UI | 待开发阶段确认 | 保持轻量，优先可访问性与响应式布局 |
| 数据与认证 | Supabase PostgreSQL + Auth + RLS | 业务数据、登录、行级权限 |
| 文件 | Supabase Storage（P1 或确有需要时） | 课程素材与知识附件 |
| AI | OpenAI API | 结构化提取、摘要、规划、项目问答 |
| 高级语义检索 | PostgreSQL + pgvector（P2 候选） | 仅在真实数据量和检索效果证明需要后评估 |
| 部署 | Vercel + Supabase（建议） | 低运维部署；开发阶段再确认 |
| 监控 | 平台日志 + 业务审计表 | 先覆盖错误、AI 调用和关键写入 |

## 3. 逻辑架构

```text
浏览器
  │
  ▼
Next.js 应用
  ├─ 页面与 Server Components
  ├─ Server Actions / Route Handlers
  ├─ 业务服务
  │   ├─ 今日工作台
  │   ├─ 课程与工作项
  │   ├─ 依赖与交接
  │   ├─ 工作记录与日报
  │   └─ 知识库
  └─ AI 编排层
      ├─ 上下文构建
      ├─ 提示与结构化输出
      ├─ 来源引用
      └─ 确认后执行动作
          │
          ├────────► OpenAI API
          │
          ▼
Supabase
  ├─ Auth
  ├─ PostgreSQL + RLS
  ├─ Storage（按需）
  └─ pgvector（仅 P2 候选）
```

原则：浏览器不直接持有 OpenAI 密钥或 Supabase service-role 密钥。普通数据访问可使用受 RLS 保护的用户会话；需要跨表聚合、AI 编排或特权操作的逻辑在服务端执行。

## 4. 应用模块

### 4.1 身份与团队

- 使用 Supabase Auth 登录。
- 业务数据归属一个团队空间。
- 成员通过 `workspace_members` 关联工作空间和 A/B/C 职责。
- MVP 三人权限基本相同；涉及个人草稿时只允许本人查看和编辑，团队确认内容对成员可见。

### 4.2 今日工作台

工作台不是独立数据源，而是对现有事实的服务端聚合：

- 今日已确认计划；
- 分配给当前成员且未完成的高优先级工作项；
- 等待当前成员处理的交接；
- 被阻塞或阻塞他人的工作项；
- 临近课程里程碑；
- 最新的 AI 日报或计划草稿。

MVP 可以通过少量 SQL 视图或服务层查询完成。只有真实性能问题出现后才引入专用缓存或搜索服务。

### 4.3 课程项目

课程项目是聚合根，工作项、素材索引、记录、交接、知识和 AI 产物都可关联课程。课程阶段只反映宏观生命周期，不替代三个工作流的真实任务状态。

### 4.4 工作项、依赖和交接

- 工作项状态变化写入事件表，供动态、日报和审计使用。
- 依赖使用显式关联表，不把依赖列表塞进 JSON。
- 交接是独立实体，支持接收、退回修改和验收。
- 应用服务负责检查循环依赖、团队成员身份和状态转换合法性。

### 4.5 工作记录与日报

- 原始自然语言记录首先写入数据库，保存成功不依赖 AI。
- AI 解析为异步或后续请求；失败时原始记录仍可使用。
- 解析结果保存在 AI 产物中，用户确认的结构化字段再产生正式更新。
- 日报由指定日期范围内的记录与事件生成，并保存快照，避免历史日报随当前数据变化。

### 4.6 素材、知识、决策与经营数据（P1）

P1 提供课程素材索引、结构化知识、团队决策记忆和按课程/渠道记录的聚合经营数据。知识检索先使用权限过滤、元数据过滤和全文关键词；经营分析只读取已保存的真实数据，未知值保持未知。

P0/P1 不建立向量、分块或 embedding 流程。高级语义检索和 pgvector 仅作为 P2 候选，并继续服从 RLS、来源引用和最小上下文原则。

### 4.7 AI 编排层

所有 AI 能力经统一服务端模块调用，负责：

- 确认当前用户和团队权限；
- 按任务选择最小必要上下文；
- 使用版本化提示词和结构化输出模式；
- 校验返回内容；
- 保存生成记录、来源、耗时和错误；
- 将潜在写操作转换为待确认动作；
- 用户确认后调用正常业务服务执行，而不是让模型直接写数据库。

## 5. 关键数据流

### 5.1 自然语言工作记录

```text
用户输入原文
  → 服务端校验并保存 work_log
  → 创建 AI 解析请求
  → OpenAI 返回结构化建议
  → 服务端校验并保存 ai_artifact(draft)
  → 用户检查/修改/确认
  → 业务服务更新任务、阻塞或下一步
  → 写入 project_event
```

保存原文与 AI 解析解耦，避免 AI 服务波动阻断日常记录。

### 5.2 日报生成

```text
选择成员/团队与日期
  → 查询该日期的 work_logs、任务事件、交接和决策
  → 构建带来源 ID 的事实包
  → OpenAI 生成固定结构日报
  → 校验引用是否存在
  → 保存 report 草稿及来源
  → 用户编辑并确认
```

### 5.3 AI 合伙人问答

```text
用户问题
  → 判断当前课程和意图
  → 检索用户有权访问的项目事实与知识
  → 模型生成“事实 / 推断 / 建议”及引用
  → 展示回答
  → 若包含写操作：生成 action proposal
  → 用户确认后由业务服务执行
```

## 6. API 与服务边界

开发阶段可按以下领域组织代码，但不需要拆成独立服务：

- `dashboard`：首页聚合查询。
- `projects`：课程、阶段、里程碑。
- `work-items`：任务、状态、依赖、阻塞。
- `handoffs`：交接、接收、退回、验收。
- `work-logs`：原始记录与关联。
- `reports`：个人/团队日报与明日计划。
- `knowledge`：知识条目与检索。
- `ai`：上下文、提示词、结构化输出、引用、动作提案。

领域服务校验业务规则；数据库 RLS 负责最后一道数据隔离。不要把关键规则只写在客户端。

## 7. 权限与安全

### 7.1 基本权限模型

- 所有业务表带 `workspace_id`，或可通过父实体可靠地推导工作空间。
- RLS 只允许当前用户访问其有效成员关系对应的团队数据。
- 私人草稿通过 `created_by` / `owner_id` 进一步限制。
- service-role 只在可信服务端使用，不出现在浏览器或日志。

### 7.2 AI 数据安全

- 只发送完成当前请求所需的上下文。
- 对敏感字段建立明确的排除策略。
- 保存来源 ID 和必要的调用元数据；是否保存完整提示与响应在开发前确认数据策略。
- 将检索到的文档视为数据，而不是可执行指令，降低提示注入风险。
- 模型输出经过结构校验和权限校验，不能直接执行任意数据库或外部系统操作。

### 7.3 审计

以下行为至少保留操作者、时间和前后状态：

- 工作项状态、负责人和截止日期变化；
- 课程阶段变化；
- 交接提交与验收；
- AI 建议被确认后产生的正式写入；
- 知识条目确认或归档。

## 8. 后台任务策略

P0/P1 采用用户主动触发和同步/受控异步请求，不引入 Cron、定时自动化或复杂队列：

- 用户提交记录后可立即触发解析，但解析失败不回滚记录。
- 日报由用户主动生成。
- 任务必须幂等，重试不能产生重复日报、重复任务或重复向量。

Cron、定时日报、自动通知、向量生成任务和跨平台自动发布全部归入 P2，只有获得新的产品确认后才设计和实现。

## 9. 性能与可靠性

三人团队数据量较小，优先正确性和可维护性：

- 对 `workspace_id`、`course_project_id`、`assignee_id`、`status`、`due_at` 和时间字段建立必要索引。
- 首页聚合查询限制时间范围和返回条数。
- AI 调用设置超时、可重试错误分类和用户可理解的失败状态。
- 核心功能在 OpenAI 不可用时仍可手动记录、管理任务和交接。
- 历史日报保存快照，不依赖实时重算。

## 10. 可观测性

首版关注少量关键指标：

- 页面/API 错误率和慢查询。
- AI 请求成功率、耗时、token/成本、结构校验失败率。
- AI 草稿的接受、编辑、拒绝及原因。
- 日报生成与确认耗时。
- 交接停留时间和阻塞时长。

不把这些数据用于个人绩效排名，而用于发现流程和产品问题。

## 11. 测试策略

- 单元测试：状态转换、依赖循环、计划排序、AI 输出校验。
- 集成测试：RLS、团队隔离、交接流程、AI 草稿确认后写入。
- 端到端测试：创建课程 → 分配任务 → 记录进展 → 交接 → 生成日报 → 确认明日计划。
- 提示词评估：使用匿名化固定样例验证事实性、引用、角色边界和缺失信息处理。

## 12. 演进边界

只有出现真实需求时才演进：

- 数据量或查询压力证明确有必要，再引入缓存或搜索服务。
- AI 后台任务明显增多，再引入专用队列。
- 文件协作成为主要痛点，再增强 Storage 和版本管理。
- 团队扩大并出现差异化权限，再细化角色权限。
- 外部发布重复工作被验证为高频痛点，再接入内容平台。
- 进入 P2 且真实需求成立后，再评估 pgvector、Cron 和定时自动化。

当前不设计微服务、事件总线、通用工作流引擎、多租户计费和插件系统。
