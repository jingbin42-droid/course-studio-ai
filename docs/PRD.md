# Course Studio AI 产品需求文档（PRD）

## 1. 文档状态

- 版本：0.1
- 阶段：产品规划草案
- 面向团队：A、B、C 三人课程创作团队
- 技术方向：Next.js、TypeScript、Supabase、OpenAI API
- 本轮范围：定义产品，不进入开发

## 2. 产品定义

Course Studio AI 的最终定位是：**AI 课程团队工作与经营中枢**。

它服务由 A（课程制作）、B（宣传与视觉）、C（上线与运营）组成的三人课程创作与销售团队，把“今天各自要做什么”“一门课程推进到哪里”和“课程经营结果如何”连接起来，让制作、宣传、发布、销售与复盘不再依赖零散聊天、口头记忆和多个孤立表格。

产品以课程项目为长期上下文，以工作项、交接、工作记录和知识为事实，以 AI 为整理、分析和规划层。

产品结构概括为：**一个课程项目、两个业务闭环、一个 AI 全能合伙人**。

- **团队工作闭环**：每日工作规划 → 执行任务 → 自然语言记录 → AI 整理 → 个人日报 → 团队日报 → 明日计划 → 次日执行。
- **课程经营闭环**：课程定位 → 课程制作 → 宣传推广 → 上线销售 → 经营数据记录 → AI 分析 → 优化建议 → 确认后创建改进任务。
- **AI 全能合伙人**：理解三人职责和完整课程上下文，在权限范围内连接两个闭环，但不绕过用户确认修改正式数据。

两个闭环共享同一个课程项目、成员权限、工作项、交接、业务日期和数据库，不建设彼此割裂的“项目系统”与“经营系统”。

它不是 CRM：不管理客户线索、销售机会和跟单过程；也不是重型项目管理系统：不要求团队花大量时间配置流程或维护字段。

## 3. 业务现状与核心问题

### 3.1 典型现状

- A 完成脚本或视频后，通过聊天告诉 B、C，但交付物、版本和接收状态容易散落。
- B 的海报、文案、短视频依赖课程卖点和素材，若上游变更，返工风险高。
- C 的上架、排期和运营依赖课程成片及宣传物料，常常只能临时追问。
- 每个人知道自己做了什么，但团队很难快速形成可靠的全局日报。
- 第二天做什么往往靠临时讨论，阻塞和关键依赖未被优先处理。
- 模板、品牌规范、复盘结论存在不同文件或聊天中，复用成本高。

### 3.2 要解决的核心问题

1. 每个成员打开系统后，能立刻知道今天最重要的工作。
2. 所有人能看到课程从制作到运营的统一状态和关键里程碑。
3. 交付和接收变得明确，减少“我以为你知道”和“还在等什么”。
4. 日常记录足够自然，AI 自动整理但不篡改事实。
5. AI 从真实项目数据生成日报、明日计划和风险建议。
6. 团队经验可以在后续课程中被检索、引用和复用。
7. 有真实经营数据时，团队可以将渠道结果与制作、宣传和销售动作关联，形成下一轮改进任务。

## 4. 产品目标与非目标

### 4.1 MVP 目标

- 支持 owner 创建三人团队、邀请另外两名成员，并为三人设置 A/B/C 业务职责。
- 建立三个人每天都会使用的“今日工作台”。
- 打通一门课程从立项到运营的可视化工作流。
- 用自然语言完成低负担的每日工作记录。
- 自动生成可追溯、可编辑的个人日报和团队日报。
- 生成以依赖和优先级为依据的明日工作建议，并由成员确认。
- 支持明确的任务依赖和工作交接。
- 让 AI 能基于当前课程事实回答问题、辅助宣传草稿并提出行动建议。

### 4.2 非目标

- 客户、销售线索、商机、合同、回款等 CRM 能力。
- 复杂绩效、考勤、工时计费和成员排名。
- 面向大型组织的多级审批和自定义工作流引擎。
- 替代专业视频剪辑、海报设计或内容发布工具。
- 在 MVP 中自动跨平台发布内容。
- 无人确认地让 AI 分派正式任务、修改负责人或承诺截止时间。
- 复杂评论、自动通知、定时日报、知识库向量检索和多 Agent 自动执行。
- 在运营数据中保存客户姓名、电话、聊天内容等个人隐私数据。

## 5. 用户与职责

### 团队初始化与双重角色

1. 首位管理员创建团队，并自动成为该团队的 `owner`。
2. owner 选择自己的 A/B/C 业务职责，邀请另外两名成员并预设其业务职责。
3. 受邀成员首次登录并接受邀请后，关联到同一个团队，团队角色为 `member`。
4. `owner` / `member` 表示系统管理权限；A/B/C 表示日常业务职责，两者相互独立。
5. MVP 中 owner 负责成员邀请和团队设置；三名成员对课程协作数据拥有相同的日常业务能力，私人记录除外。

团队使用 IANA 时区标识配置团队级时区。所有日报、工作记录和明日计划统一使用团队业务日期，不能把 `Asia/Shanghai` 写死为所有团队的唯一时区。

### A：课程制作负责人

关心：选题是否明确、脚本是否可录、录课和剪辑进度、B/C 是否拿到正确素材。

高频动作：创建或更新制作工作项、提交脚本/成片、记录制作问题、向 B/C 交接素材、查看反馈。

### B：宣传与视觉负责人

关心：课程卖点、视觉口径、所需素材是否齐全、宣传物料排期、是否因课程变更而返工。

高频动作：接收素材、制作海报/文案/短视频、提交物料、请求审核、沉淀品牌和文案经验。

### C：上线与运营负责人

关心：课程和宣传资产是否可发布、上线清单、渠道排期、发布后的数据和用户反馈。

高频动作：验收交付物、执行上架和发布、记录运营动作与反馈、发起改进任务、完成课程复盘。

## 6. 核心产品结构

### 6.1 今日工作台

首页不是项目列表，而是同时覆盖工作、经营和 AI 协作的当日决策界面：

1. **今日团队工作**
   - 今日最重要的 1–3 项工作；
   - 待我处理的交接、审核和退回修改；
   - 谁在等待谁；
   - 当前阻塞、解除条件和受影响的下游工作；
   - 快速自然语言记录。
2. **课程经营状态**
   - 活跃课程的当前阶段和关键里程碑；
   - 距离课程上线还缺少的任务、依赖和验收；
   - 距离正式销售还缺少的定价/购买链路、宣传、发布和运营准备；
   - P1 在存在真实数据时展示渠道与销售结果摘要。
3. **AI 全能合伙人**
   - 基于真实项目数据主动指出风险、信息缺口和等待关系；
   - 回答课程项目问题；
   - 提出少量、带依据的下一步建议；
   - 生成需要用户确认的任务、交接或工作调整提案。

工作台支持“我的视图”和“团队视图”。我的视图强调当前用户的行动；团队视图强调共同目标、跨角色依赖和课程经营状态，不做成员绩效排名。

没有真实数据时，首页显示“暂无数据”“尚未记录”或待补充事项，不允许生成虚构的曝光、订单、销售额、任务完成率或健康百分比。

### 6.2 课程项目空间

每门课程只有一个共享项目空间，包含：

- 课程目标、受众、核心承诺和负责人。
- 当前阶段、目标上线日期和关键里程碑。
- 按制作、宣传、上线运营三个工作流分组的工作项。
- 课程素材与链接，标明类型、版本、状态和用途。
- 依赖关系、交接记录、决策和风险。
- 与该课程相关的工作记录、AI 摘要和复盘知识。

项目空间同时提供“阶段概览”和“工作项列表”。MVP 不做自由配置的看板引擎。

### 6.3 工作项、依赖与交接

工作项是团队承诺的最小可追踪单位，至少包含标题、所属课程、负责人、状态、优先级和可选截止日期。

- **依赖**表示一个工作项开始或完成前所需的另一个工作项。
- **交接**表示某位成员把具体产出交给另一位成员，需要接收人确认“已收到 / 需修改 / 已验收”。
- 一个任务完成不等于交接完成。例如 A 完成成片后，C 仍需确认文件、版本和上线可用性。
- 阻塞必须记录原因；解除阻塞时保留历史。

### 6.4 自然语言工作记录

成员可随时输入一段话，例如：

> 上午完成第 2 章录制并上传初剪，发现案例数据需要更新；等 C 确认新版数据，明早先剪第 1 章。

系统保存原文，AI 提取建议结构：

- 已完成事项；
- 关联课程和工作项；
- 阻塞或风险；
- 下一步；
- 可能需要创建的任务或交接。

用户可以快速修正和确认。未确认的提取结果不能自动改变正式任务状态。

工作记录可选择 `team` 或 `private`。私人记录只有作者本人可以查看，不能进入团队日报，也不能作为其他成员 AI 回答的上下文。默认业务日期按团队时区计算；成员补记历史工作时可明确选择所属业务日期。

### 6.5 AI 个人日报与团队日报

个人日报从当日工作记录、工作项变化、交接事件和已确认计划中生成，包含：

- 今日完成；
- 推进中；
- 阻塞与需要协助；
- 明日建议；
- 来源引用与信息缺口。

团队日报聚合三人事实，突出：

- 今日课程整体进展；
- 跨角色交付；
- 当前风险和等待；
- 重要决策；
- 明日团队共同重点。

日报可编辑、确认和分享。AI 不应把“计划”写成“已完成”，也不应掩盖成员之间的不同描述。

MVP 日报由用户主动点击生成，不设置定时任务。个人日报可读取本人有权访问的团队记录和本人私人记录；团队日报只读取团队可见的记录、项目事件和交接，绝不读取任何私人记录。日报日期按团队业务日期确定。

### 6.6 AI 明日工作规划

每日收尾时，AI 根据以下信息生成每人的明日计划草稿：

- 未完成且已承诺的工作项；
- 即将到期的里程碑；
- 依赖链和等待关系；
- 当日记录中的“下一步”；
- 角色职责与个人可用性（若已提供）。

建议应控制数量，默认给出 1–3 个重点和必要的跟进项，并说明排序理由。成员确认后，计划才进入次日“今日聚焦”；调整计划不会自动修改原任务截止日期。

计划项与正式工作项遵循以下规则：

- 对已有工作项的安排必须引用原 `work_item_id`，不复制创建新任务。
- AI 发现需要新增任务时，只生成“新任务提案”；用户确认后才创建正式工作项，并将新任务 ID 回写到计划项。
- 纯建议只保留在计划中，不自动创建工作项。
- 只有已确认的明日计划才会在对应团队业务日期出现在首页。
- 确认、调整或完成计划都不得自动修改原工作项的截止日期；截止日期变更是独立的待确认动作。

### 6.7 AI 全能合伙人

AI 合伙人不是一个脱离数据的通用聊天框。它应能在权限范围内使用：当前用户、课程项目、工作项、记录、交接和知识库上下文。

典型问题：

- “这门课程离上线还差什么？”
- “B 今天最需要 A 提供什么？”
- “根据上次复盘，当前宣传页还缺哪些内容？”
- “帮我把这段进展整理成工作记录。”
- “如果目标上线日不变，明天三个人分别优先做什么？”
- “距离课程正式销售还需要完成什么？”

回答应区分事实、推断和建议，引用关键来源，并对写入系统的动作先展示预览、等待确认。

具体能力边界：

- **项目理解**：理解 A/B/C 职责、课程阶段、里程碑、任务、依赖、交接和版本历史。
- **工作协作**：整理记录、生成日报、规划明日工作，提出任务、交接和调整建议。
- **项目问答**：回答进度、等待关系、上线/销售缺口、近期变化和风险。
- **宣传辅助**：基于已确认的课程定位和素材起草宣传文案、短视频结构或详情页框架；草稿不会自动发布。
- **经营分析（P1）**：只在存在真实聚合数据时分析渠道曝光、点击、咨询、订单和销售额，给出宣传效果结论与改进建议。
- **改进闭环（P1）**：把经营分析转成候选改进任务或交接，用户确认后才写入工作闭环。

### 6.8 团队知识库

知识库沉淀可复用内容：

- 课程策划和脚本模板；
- 品牌规范、海报尺寸、文案口径；
- 录课、剪辑、上架和发布清单；
- 渠道规则和运营方法；
- 课程复盘、常见问题和决策记录。

知识条目可关联课程、标签和来源。P1 支持文本、外部链接和轻量素材索引；文件上传和复杂版本管理可后置。AI 回答优先引用已确认的团队知识，草稿知识需要明确标识。

P1 使用 `knowledge_entries` 的 `decision` 分类保存团队决策，不增加独立决策系统。决策记录至少包含：决策内容、决策原因、参与成员、影响范围、关联工作项和后续跟进。AI 可检索并引用已确认决策，但不得把讨论草稿当作最终决定。

### 6.9 轻量运营数据（P1）

P1 支持按课程、渠道和业务日期记录：渠道曝光、点击、咨询、订单、销售额及宣传效果复盘。经营数据必须关联课程，允许标记数据来源和统计周期；未知值保持为空，不能用 0 或 AI 推测代替。

AI 在真实数据存在时计算或解释点击率、咨询转化、订单转化等简单指标，比较渠道和时间段表现，指出可能的宣传问题，并生成优化建议。建议创建课程内容、宣传物料或运营调整任务时仍需用户确认。

该能力不是 CRM：只保存聚合指标和复盘，不建立客户档案，不存储姓名、电话、账号、聊天内容或订单明细中的个人隐私信息。

### 6.10 两个闭环的连接规则

- 每项工作、交接、日报、决策和经营数据都关联同一个课程项目或团队上下文。
- 经营数据是结果事实，任务和交接是执行事实；AI 可以分析两者关系，但不能把相关性描述为已证实的因果关系。
- AI 优化建议首先保存为草稿；需要执行时生成新任务提案，用户确认后进入工作闭环。
- 改进任务完成后的后续经营数据用于验证效果，形成下一轮复盘。

## 7. 关键用户故事与验收标准

### US-01 查看今日重点

作为任一成员，我希望打开首页就看到今天的重点、阻塞和待处理交接，以便不再从聊天记录中拼接工作。

验收标准：

- 默认只展示当前成员相关内容，并可切换团队视图。
- 今日重点可看到课程、优先级、状态和依赖提示。
- 待处理交接和“有人在等我”的事项醒目但不过度打扰。

### US-02 管理课程全流程

作为团队成员，我希望在一个课程项目内看到制作、宣传、上线运营的共同进度。

验收标准：

- 每个工作项属于一个课程项目和一个工作流分组。
- 项目概览展示当前阶段、目标日期、三条工作流状态和风险。
- 阶段变化有记录，且不会删除历史工作项。

### US-03 快速记录工作

作为团队成员，我希望用自然语言记录一天的工作，而不是填写复杂表单。

验收标准：

- 原始文本立即保存且可编辑。
- AI 可建议关联、完成项、阻塞和下一步。
- 正式任务变更必须由用户确认。

### US-04 生成日报

作为成员或团队，我希望主动触发 AI 生成基于事实的日报，减少汇总时间。

验收标准：

- 日报明确区分完成、进行中、阻塞和计划。
- 关键内容可追溯到工作记录或项目事件。
- 用户可编辑、确认、重新生成；确认版本保留。

### US-05 明日规划

作为团队成员，我希望获得少量、解释清楚的明日工作建议。

验收标准：

- 建议考虑截止日期、依赖和角色职责。
- 每条建议说明原因和来源。
- 只有确认的建议会出现在次日工作台。
- 已有任务计划引用原任务；新任务提案确认后才创建；确认计划不修改任务截止日期。

### US-06 完成交接

作为交付方和接收方，我希望明确某项产出是否已被接收和验收。

验收标准：

- 交接包含交付人、接收人、关联任务、产出链接和说明。
- 接收人可确认收到、要求修改或验收通过。
- 交接状态变化进入项目动态，并影响相关阻塞提示。

### US-07 使用 AI 合伙人

作为团队成员，我希望向 AI 询问项目状态和下一步，并得到基于团队事实的回答。

验收标准：

- 回答仅使用当前用户可访问的数据。
- 重要事实提供来源引用；信息不足时明确说明。
- 创建或修改正式数据前展示动作预览并要求确认。

## 8. MVP 优先级

### P0：形成每日协作闭环

- owner 创建团队、邀请两名成员、成员首次登录入队，以及 owner/member 与 A/B/C 双重角色。
- 今日工作台的个人和团队视图。
- 课程项目、工作项、状态、优先级与负责人。
- 工作项依赖、阻塞原因、交接与完整 `handoff_events` 历史。
- 自然语言工作记录及 AI 结构化建议。
- 用户主动触发的 AI 个人日报、团队日报和明日计划草稿。
- 明日计划对已有任务的引用、新任务确认创建和次日首页展示。
- AI 合伙人的项目问答与只读检索。
- 团队级时区、业务日期和私人记录隔离。
- 基于已确认课程信息的轻量宣传文案/结构草稿，不包含自动发布。

### P1：增强复用与项目洞察

- 课程素材库：课程资产索引、版本和外部链接管理。
- 团队知识库：文本、来源、标签和课程关联，不引入向量检索。
- 团队决策记忆：使用 `knowledge_entries.decision`，包含原因、参与人、影响范围、关联任务和跟进。
- 课程风险摘要与阶段检查清单。
- AI 合伙人在问答中提出创建任务或交接的动作建议，经确认后写入。
- 按课程和渠道记录曝光、点击、咨询、订单、销售额和宣传效果复盘，不保存客户个人数据。
- AI 经营分析、宣传效果分析、优化建议，以及确认后创建改进任务。

### P2：验证后再考虑

- 文件上传与更完整的版本管理。
- 日历、消息或内容平台集成。
- 运营指标看板和跨课程趋势。
- 更细的通知偏好与自动化。
- 知识库向量检索、多 Agent 自动执行及其他高自主性能力。
- 第三方平台经营数据集成和外部内容自动发布。

## 9. 成功指标

MVP 试用四周后，以团队实际感受和少量行为指标判断：

- 三位成员每个工作日至少一次使用今日工作台。
- 大部分关键交付通过系统交接，而非只在聊天中口头通知。
- 个人日报平均确认耗时低于 3 分钟，团队日报无需重新人工汇总。
- 因“未看到、未收到、不知道版本”造成的遗漏明显减少。
- 团队能在 1 分钟内回答任一活跃课程的当前阶段、下个里程碑和主要风险。
- AI 建议被编辑或拒绝的原因可观察，用于改进，而不是只追求接受率。
- 没有经营数据的课程不会显示虚构数字、完成率或 AI 估算销售结果。

## 10. 关键产品规则

1. 一门课程对应一个统一项目，不为 A、B、C 分别创建孤岛项目。
2. 工作记录的原文是事实来源之一，AI 结构化内容是可修正的派生数据。
3. “任务完成”“产出已交付”“接收方已验收”是三个不同事件。
4. 团队日报只能聚合有来源的数据；没有记录时明确提示信息缺口。
5. AI 建议默认不改变正式数据，用户确认后才执行。
6. 阻塞、依赖和交接在首页的优先级高于普通动态。
7. 个人视图用于行动，团队视图用于协调，不做绩效监控。
8. 私人记录只有本人可见，团队日报和其他成员的 AI 上下文不得读取。
9. 团队业务日期以团队 IANA 时区为准；历史业务日期不因之后修改时区而重算。
10. 正式销售准备与课程上线准备分别展示，但都由课程里程碑、任务、依赖和交接推导，不增加复杂流程引擎。
11. 经营数据只能来自人工录入或已确认的数据源；未知值保持为空，AI 不得补齐或编造。
12. 经营分析生成的优化建议必须经人确认，才能创建改进任务并回到工作闭环。

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 维护任务的成本高于收益 | 减少必填字段；允许从自然语言记录中建议更新 |
| AI 把推测写成事实 | 强制来源引用，区分事实/推断/建议，写入需确认 |
| 首页信息过载 | 默认只显示今日、阻塞、待处理和临近里程碑 |
| 三条工作流再次形成信息孤岛 | 所有内容绑定同一课程，跨角色依赖可见 |
| 团队知识过时 | 标记负责人、状态和更新时间；回答优先引用已确认内容 |
| 过早建设复杂系统 | 按 P0 闭环实施，所有扩展以真实使用证据为前提 |
| 私人记录进入团队摘要 | RLS 限制本人访问，团队日报查询显式排除 `private` |
| 计划确认产生重复任务 | 已有任务引用 ID，新任务必须单独确认，纯建议不创建任务 |

## 12. P0 开发任务包

1. **工程与安全基础**：Next.js/TypeScript 工程、环境变量、Supabase 客户端、服务端密钥边界、测试和错误处理。
2. **团队初始化**：注册登录、创建团队、邀请两名成员、接受邀请、owner/member 与 A/B/C 职责、团队时区。
3. **课程与执行数据**：课程、里程碑、工作项、状态、负责人、依赖、阻塞和项目事件。
4. **交接闭环**：提交、收到、要求修改、重新提交、验收、取消及完整事件历史。
5. **今日工作台**：个人/团队视图、今日重点、待处理、等待关系、阻塞、上线/销售缺口；无数据时展示真实空状态。
6. **自然语言记录**：团队/私人记录、业务日期、AI 结构化建议和确认后更新。
7. **日报与明日计划**：主动生成个人/团队日报，计划引用已有任务，新任务提案确认创建，纯建议不建任务。
8. **AI 全能合伙人 P0**：项目问答、来源引用、宣传草稿、事实/推断/建议区分、动作预览与确认。
9. **端到端验证**：用一门真实课程完成从团队初始化到次日计划的全流程试用。

## 13. P0 阶段验收标准

### 阶段 A：工程与身份

- 三个测试账号能够注册或受邀登录并进入同一团队。
- owner 能管理邀请和团队设置；member 不能执行 owner 专属操作。
- RLS 测试证明其他团队和他人私人记录不可访问。
- 团队时区能够正确生成业务日期。

### 阶段 B：人工协作闭环

- 能创建课程、里程碑、任务、依赖和阻塞。
- 能完成一次包含退回修改和重新提交的交接，旧反馈保持可见。
- 任务完成、产出提交和接收方验收是三个独立状态。
- 首页能从真实数据计算等待关系与上线/销售缺口，空数据不显示虚构值。

### 阶段 C：记录与 AI 整理

- 原始工作记录先保存，AI 失败不会导致记录丢失。
- 私人记录只对作者可见且不会进入团队日报。
- AI 结构化结果包含来源，正式状态变化必须逐项确认。
- AI 无法直接执行 SQL 或绕过业务服务。

### 阶段 D：日报与计划

- 用户能主动生成、编辑和确认个人日报及团队日报。
- 团队日报只使用团队可见事实，并标明冲突和信息缺口。
- 已确认计划在次日首页出现；已有任务引用原 ID，新任务确认后才创建。
- 计划确认不会修改原任务截止日期。

### 阶段 E：AI 合伙人与试点

- AI 能回答课程进度、等待关系、上线/销售缺口并引用真实来源。
- AI 能基于已确认课程内容生成宣传草稿，但不能自动发布。
- 所有任务、交接和调整建议先预览、确认，再由业务服务写入。
- 一门真实课程完成至少五个连续工作日试用，三名成员均能完成每日闭环。

## 14. 待产品负责人确认

- 课程阶段名称是否符合团队日常用语。
- 工作项是否需要“审核人”，还是以交接接收人和交接事件反馈满足 MVP。
- 日报的默认生成时间和确认习惯。
- 团队现有素材通常存放在哪里，MVP 是否只保存链接即可。
- 首个试点课程及其计划上线日期。
- “课程上线”和“正式销售”的团队定义、目标日期和完成标准。

这些问题不阻碍当前规划，但会影响下一阶段的原型和实现细节。
